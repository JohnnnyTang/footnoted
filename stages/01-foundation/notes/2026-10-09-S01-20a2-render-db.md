## Summary

**What did not land, or needs care:**
- **No pass/fail.** Every render number here is *emulator* (`fn_api36`, profile) and decides nothing. The emulator was in its "slow" state for the whole batch: about 51–54 fps and 15–25 % of frames over 32 ms, **with the fog off as well**.
- **The main finding is a latency problem, not a frame-rate problem.** On layout B, one fog update in every z10 pass waits **4.8–6.2 s** for its tile queries (emulator). The cause is the spans query. Mexico City's z10 tile row holds 319,537 of the 458,360 per-segment spans, and every tile in that row scans all of them. The frame rate does not suffer, because the queries run on a worker isolate. The fog for those tiles still arrives seconds late. This needs a deduplicated read model (union spans or the F01.3 rollups) before G1-B(e); see S01-V20a2a.
- **The z5 spot run issued no fog updates during its passes.** At z5 the whole path fits inside the padded tile set, so z5 never exercises the query during the pan (S01-V20a2c).
- **One run was contended and repeated.** A sibling's CPU load overlapped run `013205` (z10 holes VD B). I moved that run to `evidence/S01-20a2/contended/`, repeated it as `021129`, and regenerated `criterion2.md` and `runs.md` by hand afterwards. That means the step's committed output is no longer exactly what the driver wrote; details under Measurements.
- **Two small changes are not covered by a full driver run.** The measured APK was built at `7228ae4`. `738b8ae` (strip `dart run` noise before the table in `runs.md`) and `f907ba3` (keep the key out of a `PRAGMA key` error message) came after it. Neither touches a measured code path; both are covered by analyze and the unit tests only.

**What landed:**
- `render_bench` builds a keyed SQLCipher coverage database from `dataset.segcells.bin`, once and outside the passes. It uses storage_bench's layout B by default and layout A by a switch (`layout` extra / `RB_LAYOUT`).
- The fog reads coverage only through the tile query, on a worker isolate. The fog's tile cache is emptied at the start of every pass, so every measured pass does I/O.
- `cipher_version` is read back from the fog's own connection. It appears in every run log (`RENDER_BENCH_DB`), in `app_result.json` and in `criterion2.md`.
- The pan now crosses Mexico City and follows the CDMX → Monterrey corridor at a constant screen speed. z5/z14/z18 spot runs are available.
- `spike/device_run/render.dart` implements the render step. The dry run on the emulator completed with exit 0 and no manual step.
- render_bench tests: **+9 (9 → 18)**.

The `(y, x_start)` index bounds only `y`. The per-segment spans repeat every commute, so Mexico City's rows hold about 1,300 spans each. A padded z10 set has 5–7 tiles in row 455, and that update costs ≈1.5 s on the desktop and ≈5–6 s on the emulator. Layout A's x-strip scan is the S01-11 finding at full scale: 5 M rows per tile column, because the CDMX → Monterrey corridor runs north–south.

**Observations for G1-B(e):**
- Fog reads need a read model without per-segment repetition: the union of spans (36,590 rows at z20, S01-10) or the F01.3 rollups (`cell_rollups` at 16/12/8), keyed so a tile is a bounded range. The per-segment tables are the write/provenance model (invariant 6).
- Off the UI isolate is necessary. A 5 s query on the UI isolate would be a 5 s freeze.
- TextureView again has more frames over 32 ms than VD (19.6–25.1 % vs 15.4–21.3 %), the same direction as S01-12 but a smaller gap in this slow state.
- z14 and z18 frame rates are lower than z10. There is no fog-off control at those zooms, so this is not attributed to the fog; the base map also loads denser tiles there.
- On 2026-10-09 15:11Z, a one-off validation run (an earlier build, before the per-pass cache clear; scratch output, not evidence) gave 58.9–59.5 fps / 0.5–1.3 % in the emulator's "fast" state. Absolute emulator numbers swing with that state, as S01-12 found.
